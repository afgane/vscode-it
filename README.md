# VS Code as a Galaxy Interactive Tool

Visual Studio Code (OpenVSCode Server) packaged as a Galaxy Interactive Tool
(IT). Supports both path based and domain name based installations.

## Layout

| Path | What it is                                                                                                             |
|---|------------------------------------------------------------------------------------------------------------------------|
| `tool/interactivetool_vscode.xml` | The tool definition (ToolShed-ready with `tool/.shed.yml`)                                                             |
| `tool/macros.xml` | defines: `@CONTAINER@`, `@TOOL_VERSION@`, `@REQUIRES_DOMAIN@`                                                          |
| `install.sh` | Copies `tool/` into a Galaxy tool directory with `mode` and `image` set                                                    |
| `config/galaxy.yml` | The `interactivetools_*` settings for each mode                                                                        |
| `config/job_conf.yml` | Docker and Kubernetes destinations that can run ITs                                                                    |
| `config/tpv_rules.yml` | Total Perspective Vortex equivalent of the routing                                                                     |
| `config/nginx.conf` | nginx fragments for conventional servers (gx-it-proxy), both modes                                                     |
| `config/tool_conf.xml` | Toolbox file adding the tool to an "Interactive Tools" section                                                         |
| `docker/` | The image: gitpod/openvscode-server plus Python, R, micromamba, gcloud, extensions, `start.sh`, `galaxy-get`, `galaxy-put` |
| `helm/vscode-it.yml` | galaxy-helm values overlay, GENERATED by `scripts/render_helm.py`                                                      |
| `scripts/render_helm.py` | Renders the overlay from `tool/` so the two cannot drift                                                               |

## How it works

1. The user runs the tool, optionally selecting datasets from the current history. 
2. Galaxy creates an
   entry point and injects that path into the container as `EP_PATH`, along with `API_KEY`,
   `GALAXY_URL` and `HISTORY_ID`. For a domain-based
   entry point the injected path is empty which the tool command turns into
   `/`.
2. The tool command links the selected datasets read-only into
   `workspace/inputs/` and runs `start.sh`.
3. `start.sh` puts HOME, the server data directory, the user data directory and
   the micromamba root under the job working directory, because the container
   runs as Galaxy's job uid rather than the image's user. It writes a
   `.bashrc`, a `settings.json` and a `workspace/README.md` once, then execs
   `openvscode-server --server-base-path "$EP_PATH"` on port 3000.
4. The job destination exposes port 3000. On Kubernetes the runner creates one
   Service and one Ingress per session; on a Docker destination Galaxy's
   gx-it-proxy forwards to the host/port reported by the container monitor
5. Stopping the session from User > Active Interactive Tools ends the job.
   Files saved under `workspace/outputs/` with an extension are imported into
   the history as a collection.

## Installing

### 1. The tool

Either install from the ToolShed once the repository is published
(`interactive_tool_vscode`, see `tool/.shed.yml`; publish with
`planemo shed_create --shed_target toolshed tool/` and update with
`planemo shed_update`), or copy it into the tool directory:

    ./install.sh --mode path   --tool-path /srv/galaxy/server/tools
    ./install.sh --mode domain --tool-path /srv/galaxy/server/tools --container ksuderman/galaxy-vscode:1.105.1-4

The installer writes `tools/interactive/vscode/` and prints what is left to do.
Add the tool to a tool conf (`config/tool_conf.xml`) and restart Galaxy.

### 2. galaxy.yml

Merge the keys from `config/galaxy.yml`: `interactivetools_enable`, a shared
`interactivetools_map`, and for the chosen mode `interactivetools_proxy_host`
and `interactivetools_upstream_proxy`. The comments in that file say which
values go with which mode and which kind of server.

### 3. A destination that can expose a port

Kubernetes (`KubernetesJobRunner`) or a Docker-enabled local, Slurm or Pulsar
destination. `config/job_conf.yml` has both, with the runner settings a
WebSocket-heavy IDE needs; `config/tpv_rules.yml` is the TPV equivalent. Cloud
batch runners such as GCP Batch cannot run ITs because nothing reports the
container's host and port back to Galaxy and nothing can route browser traffic
to the VM.

### 4. The proxy

- Conventional servers: run gx-it-proxy (the galaxyproject.galaxy role starts
  it through Gravity) and add the fragment for your mode from
  `config/nginx.conf`. Domain mode also needs the wildcard DNS record
  `*.ep.interactivetool.<host>` and a certificate covering it; Let's Encrypt
  issues wildcards only through the DNS-01 challenge.
- Kubernetes: nothing to add for path mode. For domain mode point a wildcard
  DNS record at the ingress controller and name the wildcard certificate's
  Secret in `k8s_interactivetools_tls_secret`.

Users must be logged in; the injected API key is per user.

### galaxy-k8s-boot

Nothing to add: the role installs the tool by default. Its
`enable_interactive_tools` variable defaults to `true` (since commit 649fbc4 on
the `vscode-it` branch) and appends `mixins/vscode-it.yml`, a copy of
`helm/vscode-it.yml`, to the Helm values files. The default exists because
Leonardo on Terra passes a fixed set of extra-vars and no values files. To leave
it out, set the variable to `false`: `bin/launch_vm.sh` has no extra-vars flag,
so either run the playbook directly with
`ansible-playbook ... -e enable_interactive_tools=false` or change the default
on the branch the VM pulls. Naming the overlay explicitly with
`-f mixins/vscode-it.yml` is harmless; the role deduplicates the list.

When Galaxy is served at a real hostname with a certificate, set
`interactivetools_proxy_host` to that hostname (galaxy-k8s-boot's
`hostname-tls` branch, PR #169, does this automatically). ingress-nginx routes
by Host before path, so a host-less IT Ingress is unreachable once Galaxy's own
Ingress names a host.

## Building the image

    cd docker
    ./build.sh                      # builds ksuderman/galaxy-vscode:1.105.1-4
    docker push ksuderman/galaxy-vscode:1.105.1-4
    ../scripts/dev/test_image.sh ksuderman/galaxy-vscode:1.105.1-4

`REGISTRY`, `IMAGE_NAME`, `OPENVSCODE_VERSION` and `TAG` can be overridden in
the environment. Bump the `-<n>` suffix for every change and never move a tag:
the tool pins one, and nodes that already pulled it will not see a moved tag
with `k8s_pull_policy: IfNotPresent`. After a rebuild, set `@CONTAINER@` in
`tool/macros.xml` and run `scripts/render_helm.py`.

The tool pins `1.105.1-4`, in which `start.sh` treats an empty or unset
`EP_PATH` as `/` on its own. `1.105.1-3` and earlier insist on a non-empty
`EP_PATH`; the tool command still exports `/` when Galaxy injects an empty
path, so both modes work with those images too.

`scripts/dev/test_image.sh [IMAGE]` runs the image the way Galaxy's Docker
runner does (uid 10001, the tool script as the command) and checks path mode,
domain mode (empty `EP_PATH`) and an unset `EP_PATH`. It exits non-zero on any
failure and defaults to the image named in `tool/macros.xml`.

What is inside (Ubuntu 22.04 base from gitpod):

- `python3` with `bioblend`, `ipykernel`, `jupyter_client`; `pip`, `venv`
- R 4.5 from conda-forge at `/opt/conda/envs/r` (appended to the end of PATH)
  with `languageserver`, `IRkernel` (registered as the `ir` kernel) and
  `httpgd`
- `micromamba` at `/usr/local/bin`, with its root under the job directory
- Google Cloud CLI (`gcloud`, `gsutil`); inside a GCE VM or Terra it
  authenticates as the VM's service account through the metadata server
- `git`, `git-lfs`, `curl`, `jq`, `nano`, `unzip`, `bzip2`
- Extensions baked in: ms-python.python, ms-toolsai.jupyter, REditorSupport.r
- `/opt/galaxy-vscode/start.sh` and `/opt/galaxy-vscode/bin/galaxy-{get,put}`

The image has **no ENTRYPOINT** (only `CMD start.sh`). Galaxy's Docker runner
starts containers as `docker run ... <image> /bin/sh tool_script.sh` without
`--entrypoint`, so an entrypoint would swallow the tool script. The Kubernetes
runner sets `command` and `args` explicitly and does not care either way.

A quick smoke test without Galaxy:

    docker run --rm -e EP_PATH=/galaxy/interactivetool/ep/1/t -w /jobdir -v $PWD:/jobdir \
        --user 10001:10001 -p 3000:3000 ksuderman/galaxy-vscode:1.105.1-4
    # then open http://localhost:3000/galaxy/interactivetool/ep/1/t/
    # domain mode: -e EP_PATH=/ and open http://localhost:3000/

## CI

`.github/workflows/ci.yml` runs on every push and pull request: `xmllint`,
`planemo lint`, `bash -n` on the shell scripts, a drift check that fails when
`helm/vscode-it.yml` is not what `scripts/render_helm.py` produces, a check
that the tag in `docker/build.sh` is the pinned `@CONTAINER@` tag or one ahead
of it, and `install.sh` into a scratch directory in both modes. On a git tag it
also builds the image and runs `scripts/dev/test_image.sh` against it. It never
pushes an image.

## Keeping galaxy-k8s-boot in step

galaxy-k8s-boot embeds the tool XML in `mixins/vscode-it.yml` because
galaxy-helm mounts tool files from values. After changing anything under
`tool/`:

    scripts/render_helm.py                     # path mode, the Terra/AnVIL layout
    cp helm/vscode-it.yml ../galaxy-k8s-boot-vscode-it/mixins/vscode-it.yml
    cp docker/Dockerfile docker/build.sh docker/start.sh ../galaxy-k8s-boot-vscode-it/docker/vscode-it/
    cp docker/bin/* ../galaxy-k8s-boot-vscode-it/docker/vscode-it/bin/

The longer-term fix is for galaxy-k8s-boot to stop carrying the copies and
install the tool from the ToolShed (or this repository) instead.

## Using it

- Inputs appear under `workspace/inputs/`; outputs saved under
  `workspace/outputs/` with an extension come back to the history on Stop.
- `galaxy-get <hid|id|name>` downloads a dataset from the current history,
  `galaxy-put <file>...` uploads files to it. Both use `GALAXY_URL`,
  `API_KEY` and `HISTORY_ID`.
- Extra software: `micromamba create -n <env> -c conda-forge -c bioconda ...`.
  Bioconductor packages come prebuilt from bioconda, for example
  `micromamba create -n bioc -c conda-forge -c bioconda r-base=4.5 bioconductor-limma r-irkernel`
  (about a minute and 1.8 GB). `BiocManager::install()` of compiled packages
  fails because the image has no compilers. Register an environment's R for
  notebooks with `micromamba run -n bioc Rscript -e 'IRkernel::installspec(name="bioc", displayname="R (bioc)")'`.
- Environments and everything else outside `workspace/outputs/` live in the
  job directory and are gone when the session stops.
- Markdown preview and other webviews need a secure context. Over plain HTTP
  on an IP address the preview pane is blank; serve Galaxy over HTTPS.

## Gotchas collected while building this

- The gitpod base image's ENTRYPOINT appends any command to the stock server's
  flags. Reset it (`ENTRYPOINT []`) rather than replacing it, see above.
- The job runs as an arbitrary uid with HOME unset. Anything the server writes
  must be redirected to the job directory, and anything it reads from the
  image must be world-readable (the extensions directory is `chmod a+rwX`).
- `interactivetools_map` must be on storage every handler sees on multi-process
  or multi-pod deployments, otherwise the job handler cannot find the map the
  web handler wrote and Stop fails with "no such table: gxitproxy".
- `k8s_interactivetools_use_ssl: false` in path mode, otherwise the runner
  emits a TLS block with an empty host and secret on every IT Ingress.
- Tool XML and TPV rules mounted as ConfigMap subPaths are not picked up live;
  restart the web, job and workflow deployments after changing them.
- Galaxy hands a domain-based entry point an empty `EP_PATH`
  (`get_entry_point_path` returns `/` and the injector strips the slash), so
  anything reading it must default to `/`.

## Status

Upstream: galaxy-k8s-boot PR #167 (`vscode-it`, against dev, enabled by
default as of 2026-11-12); HTTPS support for test VMs is PR #169
(`hostname-tls`, against dev); user-defined tool roles and container allowlist
are PR #168 (`udt-roles`). The three are combined on `anvil-staging` for Terra
dev, where VS Code was confirmed working on 2026-11-12.

Verified, path mode, on a GCE VM deployed by galaxy-k8s-boot (Kubernetes
runner), over HTTP and HTTPS: launch, env vars, input links, terminal, gcloud
as the VM service account, galaxy-get/galaxy-put, R and the ir kernel,
Bioconductor via micromamba, clean Stop with output collection. On Terra dev
(Leonardo) the tool launches and the IDE works behind the proxy.

Not yet exercised: domain mode end to end (the code paths are Galaxy's standard
ones, but nobody has launched this tool at a wildcard host yet), a Docker or
Pulsar destination (the image change that makes it possible has been in since 1.105.1-3),
and a ToolShed install. The repackaging in this directory (`tool/`, `config/`,
`install.sh`, `scripts/render_helm.py`) was done 2026-11-12 and has not been
deployed anywhere.
